# MAX reactions — отдельный сервис Desiree

Единственная цель: один обычный MAX-аккаунт ставит 👍 новым публикациям
`https://max.ru/channel_animenaruto`. Это не замена `cross` и не часть
`tg-publisher`. Никакие существующие токены, `.env`, Telegram-сессии,
PostgreSQL или настройки SOCKS5 не читаются и не меняются.

## Изоляция

- Контейнер: `cross-max-reactions`; одноразовый вход: `cross-max-reactions-auth`.
- Образ: `cross-max-reactions:20261021.2`, отдельный Dockerfile и pinned requirements.
- Отдельный том: `cross-max-reactions-data:/data`; `cross-data` не подключается.
- Сеть `host`, без входящего HTTP-порта; MAX подключается напрямую, без Telegram SOCKS5.
- Лимиты: 256 МБ, 0.25 CPU, 64 PID; read-only rootfs, сброшенные capabilities.
- Конфигурация: `settings.toml`, read-only bind mount; изменение требует
  перезапуска только нового контейнера, а не пересборки `cross`.

## Подключение аккаунта — только после сборки и тестов

На сервере в `~/cross`:

```bash
bash max_reactions/manage.sh build
bash max_reactions/manage.sh auth
```

При интерактивном запуске QR отображается в терминале. Его сканируют
в приложении MAX нужного аккаунта и подтверждают вход. Если включён пароль 2FA,
он вводится скрыто в этом же терминале. SMS-коды, пароль и SQLite-сессию
не отправляют в чат. В headless-режиме `auth-bg` QR временно сохраняется
в `/data/connect.png` внутри нового контейнера; по завершении или таймауту
авторизации изображение удаляется. QR имеет короткий срок жизни.

После входа сервис вступает только в указанный публичный канал, проверяет
чтение его истории и сохраняет числовую привязку канала и аккаунта. Событие
`auth_complete` подтверждает завершение этого шага. Реакции при входе не ставятся.

```bash
bash max_reactions/manage.sh start
bash max_reactions/manage.sh status
bash max_reactions/manage.sh logs
```

Фоновый `run` не начинает новый QR-вход сам. Потеря или отзыв авторизации
требует отдельного `auth`; сессию одновременно держит только один процесс.
Для остановки: `bash max_reactions/manage.sh stop`.

## Поведение

При каждом старте фиксируется текущий момент: более старые публикации
игнорируются, включая появившиеся во время простоя. Опрос — раз в 30 секунд,
не более одной новой реакции за опрос, возраст публикации — до 15 минут.
Другие чаты и служебные сообщения отбрасываются. Выбранная вручную реакция
не заменяется. Если MAX опускает `chat_id` в ответе истории, контекст берётся
только из явно запрошенного целевого канала; явно указанный чужой ID не меняется.
Перед запросом атомарно сохраняется claim в отдельной SQLite:
ошибка, таймаут или перезапуск не повторяют сомнительный запрос для того же поста.
`reaction_confirmed` означает подтверждённую сервером реакцию;
`reaction_requested` — запрос без подтверждения в ответе. Тексты сообщений,
токены, QR-ссылки и содержимое сессии не записываются в журналы.

Тестовый режим `manage.sh dry-run` читает только историю и журналирует
подходящие новые посты, не ставит и не резервирует реакции.

## Проверка и откат

```bash
python -m unittest discover -s max_reactions/tests -q
bash artifacts/max-reactions/ROLLBACK.sh
```

Откат останавливает и удаляет только два новых контейнера. Новый том
с авторизацией сохраняется для повторного запуска; существующие контейнеры,
тома и исходники не меняются. Исходники сервиса можно убрать отдельным
обратным patch из `artifacts/max-reactions/DIFF.patch`.

SDK: [PyMax 2.4.1](https://github.com/MaxApiTeam/PyMax),
[QR-авторизация](https://docs.pymax.org/getting-started.html),
[реакции](https://docs.pymax.org/api/client-web.html#pymax.WebClient.add_reaction).
